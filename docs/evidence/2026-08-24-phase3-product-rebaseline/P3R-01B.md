# P3R-01B — Durable Process Framework

Status: accepted focused implementation evidence on macOS, 2026-08-24.

## Outcome

The enduring linked Level-G application now has one database-coordinated
controller/worker framework:

- `worker start` uses the public cREXX child-process channel to start 1 through
  32 instances of the same linked `crexx-rag` application;
- every controller and worker opens its own SQLite connection;
- migration 3 adds `runtime_instances` without changing semantic generations
  or `ragwork` item leases/fences;
- runtime identity includes kind, parent controller, host, PID, random
  process-start token, executable identity, mode and optional job filter;
- database-clock heartbeats determine live/stale classification;
- a same-host `ADDRESS CREXX ps` result is an additional diagnostic only;
- a separate application instance can list/status local and remote rows,
  request a cooperative drain, and explicitly prune terminal/stale rows; and
- the worker body truthfully reports `processor=framework-idle`.

This item does **not** attach `.ragworkprovider`, call an LLM, claim an
ingestion item, process extraction/embedding work, or close Gate 3R.

## Reused facilities

- the linked `crexx-rag.rxbin` and stable launcher from P3R-01;
- the typed command/result and `ragproduct` dispatcher;
- `ragstore` WAL, five-second busy timeout, migrations and independent
  connection ownership;
- installed `rxplatform` host/sleep operations and `ADDRESS CREXX pid/ps`; and
- the public `concurrency.channel` child-process and null-byte-endpoint APIs.

No shell owns product supervision. The shell in the focused test is only a QA
driver used to observe and forcibly terminate independent application
processes.

Each `rxvme` and `rxbvm` cell:

1. initialized a fresh schema-v3 library;
2. started one controller and two child workers;
3. observed both workers as `classification=idle` and `pid_check=alive` from a

## Remaining boundary

P3R-02 through P3R-05 still own configured provider binding, exact durable
work input, extraction/embedding processors, and replacement of the
`framework-idle` body with `runworkeronce`/`runworkerfollow`. P3R-05A owns
optional ANSI/plain progress and any interactive controller view. CRI-17 does
not block this design because these are separate OS processes, not attached
cREXX task threads.
