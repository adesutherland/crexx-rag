# P3R-01 — Enduring Installed cREXX Application

Status: accepted for the recorded macOS scope on 2026-08-24. Hosted provider
calls: **0**.

## Outcome

The maintained Level-G CLI main is now packaged as one linked
`crexx-rag.rxbin` product image. A thin installed launcher locates a CREXX VM,
the image, and its adjacent application-local provider directory; it does not
compile cREXX, enumerate modules, own configuration, run SQL, or dispatch
product operations itself.

The linked application is installed internally as
`libexec/crexx-rag/crexx-rag`. The existing native-v1 `bin/crexx-rag` remains
the default command and executable oracle. Selecting or renaming the default
command remains a later explicit cutover decision.

The same linked application also produced a CREXX-native arm64 executable and
successfully ran `library init`. No RAG algorithm moved into C or C++.

## Standard RXPA packaging

SQLite uses the normal CREXX native-provider design; there is no product bridge
or alternate signature mechanism:

1. The existing `LOADFUNCS`/`ADDPROC` block advertises all 30 qualified
   `sqlite_boundary.*` procedures, language level, return type, and typed
   argument signature to the compiler.
2. The dynamic build exports `_initfuncs` for declaration discovery and
   `_rxpa_query_v2` for the separate provider-identity and procedure-capability
   query.
3. `rxc` type-checks used calls and `rxlink` records their stable provider ID
   and signature in `crexx-rag.rxproviders`.
4. VM packaging places `rx_sqlite_boundary.rxplugin` beside the application
   image for trusted autoload.
5. Native packaging selects and force-loads the canonical
   `rx_sqlite_boundary.a` built from the same source. It links the platform
   SQLite library with `-lsqlite3`.

The v2 query deliberately returns zero for every procedure. That is a
conservative concurrency/session capability statement, not the REXX API
advertisement. Both the dynamic plugin and native executable contain all 30
qualified procedure declarations.
