Status date: 2026-08-06. `P2-03` is accepted. This evidence covers the
Level-G schema-v2 and library lifecycle foundation only. It does not accept
version-1 import, backup/restore, product repository APIs, commands, providers,
workers, sidecar publication, or plan/apply.

## Implemented Boundary

All maintained application and test logic uses `options levelg`:

- `ragschema.crexx` owns two ordered migrations and the exact schema-v2 DDL;
- `ragstore.crexx` owns migration validation, initialization, read-only and
  read-write opens, published generations, pinned read snapshots, manifest
  projection/recovery, verification, and ancestor rollback; and
- `tests/p2_03_store_scenario.crexx` is the compiled lifecycle and failure
  consumer.

Migration 1 creates library identity, non-secret configuration snapshots,
published generations, metadata, audit events, and published-generation
immutability triggers. Migration 2 creates the complete 32-table logical
schema required by the architecture: provider runs; source artifacts, texts,
revisions, maps, chunks, and FTS; candidates, concepts, aliases, mentions;
directional claims, support, conflicts, and ambiguity; embeddings and vector
generations; jobs, items, attempts, events, and reviews.

The migration checksums are SHA-256 over the exact ordered SQL statements with
one LF after each statement:

```text
1  363ee648abb5332a9085fa9afa94dc4a1c13835945fcd1dc60616d5332e41206
2  54ad8ef343027f977cd64c7b6ebd9c5bde0ad808448006ba4e891ec80478fd0d
```

The CMake proof recomputes both values from `ragschema.crexx` before compiling.
Runtime open validates every recorded version, name, and checksum. Upgrade is
transactional and ordered; current-version reapply makes no row changes;
downgrade, tampered checksums, future versions, gaps, and failed DDL are
rejected.

## Generation And Manifest Rules

SQLite is authoritative. A writer creates a staging generation and all
visibility changes in one transaction, changes its state to immutable
`published`, advances `library_meta.published_generation`, and commits before
writing `manifest.json.new` and atomically renaming it. A reader begins a
SQLite transaction, pins that pointer, and applies the same generation to all
visibility predicates.

Read-only open cannot create a missing library, apply migrations, write the
database, or repair a missing/stale/temporary manifest. Authorized recovery
regenerates the non-secret projection from SQLite. The manifest contains
bundle/schema versions, library identity and timestamps, generation,
profile identity/hash, required capability versions, empty P2-03 sidecars, and
explicit migration/recovery flags; it contains no live-database checksum or
secret.

Rollback accepts only a published ancestor and preserves monotonic generation
allocation. While holding the writer lock it first publishes a projection of
the already-committed target generation, rebuilds FTS for that generation's
visible chunk occurrences, then moves the SQLite pointer and appends an audit
event. A crash can therefore leave the manifest behind SQLite but never ahead
of it.

Orderly writer close checkpoints WAL and returns a stable bundle to rollback-
journal mode, enabling byte-for-byte zero-write read-only opens. Abruptly
terminated writers retain WAL. Crash-left read-only inspection may change only
SQLite's transient `-shm` lock page; hashes prove that the database, WAL,
manifest, temporary manifest, and all other bundle state remain unchanged.

## Verification

`verifyragstore` checks full SQLite integrity, foreign keys, migration identity,
the published-generation pointer, visibility bounds, active FTS membership and
body/content parity, embedding byte dimensions, and complete manifest/database
agreement. P2-05 will add active immutable-sidecar verification; P2-06 will add
repository-level lifecycle/orphan invariants as those APIs are implemented.

## Focused Proof

CTest target `p2_03_storage_foundation` compiles schema, store, and scenario in
optimized and non-optimized modes and runs both `rxvme` and `rxbvm`. All four
cells pass initialization, 32-table presence, migration records, pinned old/new
snapshots, non-empty source/revision/chunk/FTS generation visibility,
published-generation immutability, stale manifest reporting/recovery, full
verification before and after rollback, and ordered rollback.

Every cell also covers migration-record 1-to-2 DDL upgrade, idempotent reapply,
downgrade and checksum denial, and a forced mid-migration table conflict
proving that earlier DDL in the failed migration rolls back. Stable-library
and missing-path read-only checks compare complete recursive
file/size/mtime/SHA-256 state.

The optimized crash sequence runs both VMs as child processes and sends real
`SIGKILL` at three marker boundaries:

1. before SQLite commit: generation 1 and its manifest remain authoritative;
2. after SQLite commit: generation 2 is authoritative and the old manifest is
   reported stale without repair; and
3. after writing `manifest.json.new`: generation 3 is authoritative, the old
   manifest is `stale-temp`, and authorized recovery atomically aligns it.

The final measured focused build passed in 31.92 seconds with 180,672 KiB
maximum RSS. The focused CTest also passed in the final full run in 31.02
seconds.

preset configure commands passed normally. Debug and Release builds succeeded.

toolchain, benchmark, or oracle failure was observed.

  schema; direct SQL in the P2-03 consumer is fixture setup, not a public API.
- `P2-07` and `P2-08` own public command/result and lifecycle command surfaces.
- `P2-10` owns canonical plan digest and apply-time revalidation.
- SQLite power-loss durability inherits `synchronous=FULL` and SQLite's WAL/
  rollback-journal guarantees; no claim is made beyond the tested process-
  termination boundaries.
- CRI-15 and CRI-16 remain unchanged and separate from storage acceptance.

complete by this result.
