## Implemented Boundary

`ragrepository.crexx` is Level-G application code over the accepted generic
SQLite boundary and `ragreadsnapshot`. `repositorynames()` publishes a closed
registry of 16 repository names:

```text
sources               source-artifacts       source-revisions
normalization-maps    chunk-contents         chunk-occurrences
generations           concepts               claims
claim-support         lineage                embeddings
jobs                  job-items              attempts
reviews
```

`pagerepository()` dispatches those names to fixed SQL. The caller cannot
provide a table, projection, predicate, or ordering expression. Every opaque
cursor is bound as a typed SQLite value, is capped at 512 bytes, and advances a
stable keyset ordering. Limits are required from 1 through 100. The query asks
for one look-ahead row, returns at most the requested limit, and emits the last
returned row's opaque cursor only when more data exists.

Every page identifies its pinned semantic generation. Generation-scoped
repositories apply the same snapshot generation to source/revision/chunk,
concept/claim/support, and embedding-link visibility. Artifacts, normalized
texts, chunk content, and embedding values are returned only when reachable
from a visible occurrence. Operational job, item, attempt, and review pages use
the same SQLite read transaction, so they are transaction-consistent even
though they are deliberately not semantic-generation rows.

`ragrepositoryrecord` is a bounded typed envelope. It retains primary,
parent, and related identities, scalar state/metadata, exact `.binary` payload,
integer ordinal/metric values, and explicit visibility bounds. Artifact bytes
and vector bytes do not pass through text or whole-corpus JSON. Repository-
specific structured metadata uses bounded row-local JSON already owned by the
schema; page membership and binary values remain typed.

## Lifecycle And Orphan Verification

`verifyrepositories()` evaluates a pinned snapshot rather than whatever
generation happens to be live later. It checks:

- visible source/current-revision and revision/source membership;
- visible chunk/revision, claim/concept-endpoint, support/claim/chunk, and
  embedding/chunk membership;
- source/concept lifecycle values, support lineage/extractor identity, vector
  dimension and byte count, and published generation references;
- exact two-way FTS membership/body equality for the pinned generation;
- job, job-item, attempt, and review state/decision invariants; and
- worker/fence/lease and attempt completion coherence.

Historical immutable artifacts and content are not classified as orphans merely
because their last occurrence is no longer visible. That retention is required
for historical citation and rollback. The verifier instead rejects inconsistent
query-visible or operational relationships.

## Focused Proof

CTest `p2_06_repositories` compiles `ragschema`, `ragfile`, `ragstore`,
`ragrepository`, and its scenario with and without optimization, then runs
both VMs. Every cell builds generation 2 with two records in every repository,
pins a read snapshot, and publishes generation 3 through the already-open WAL
writer. The old transaction continues to page exactly its original two rows in
all 16 repositories, including job/review rows. A fresh transaction sees the
replacement semantic rows, three published generations, and three operational
rows.

Every repository is exhausted at a one-row limit, proving cursor progression,
page bounds, no duplicate page, and end-of-sequence behavior. Focused record
checks prove an artifact containing an embedded NUL and invalid UTF-8 byte and
an eight-byte float32 vector cross the Level-G record boundary byte-exactly.
Revision text/provenance, normalization coordinates, chunk occurrence identity,
support lineage, and job budgets are also asserted.

Negative coverage rejects an unknown repository, zero limit, 513-byte cursor,
and a closed snapshot. The test then injects a visible source whose current
revision belongs to another source plus an invented job state. Verification
reports exactly those two category faults; after repair it returns clean.

The final isolated focused four-cell CTest passed in 7.46 seconds with 227,616
KiB maximum RSS. The same test passed in 9.05 seconds during the full parallel
run.

## Full Validation

The current-host validation used the same scratch-installed package and fresh
Debug/Release build directories as P2-05:

```text
cmake -S . -B <debug> -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_PREFIX_PATH=<scratch-crexx> -DCREXX_DIR=<scratch-crexx>/lib/cmake/CREXX
cmake --build <debug> --parallel 10
ctest --test-dir <debug> --parallel 10 --output-on-failure
cmake -S . -B <release> -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_PREFIX_PATH=<scratch-crexx> -DCREXX_DIR=<scratch-crexx>/lib/cmake/CREXX
cmake --build <release> --parallel 10
git diff --check
```

Debug configure/build succeeded and the full suite passed 65/65 in 91.85
seconds. A fresh Release configure/build in a new build directory succeeded.
`git diff --check`, the donation-document audit, and the language-level audit
passed. No generated application artifact was written into the source tree.

## Remaining Limits

- These are internal repositories, not the P2-07 public command/result format.
- Repository pages are bounded by rows. Individual captured artifacts/chunks
  and vectors remain bounded by the ingestion/profile limits assigned to later
  phases; P2-06 does not add streaming BLOB reads.
- P2-06 validates operational lifecycle rows but does not implement the Phase-4
  worker claim/fence/promotion state machine.
- Exact downstream Linux confirmation remains later QA after further material
  current-host progress.

`P2-07` is next and pending. No later Phase-2 item is active or implied complete
by this result.
