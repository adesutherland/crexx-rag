# P2-05 Pinned Backup, Restore, And Immutable Sidecars

Status date: 2026-08-23. `P2-05` is accepted. This evidence covers immutable
sidecar publication, generation-pinned online backup, backed-database manifest
generation, and fresh-folder restore. It does not accept paged repositories,
public commands, providers, workers, or plan/apply.

## Implemented Boundary

`ragbackup.crexx` is Level-G application code. Sidecar publication has four
explicit boundaries:

1. copy the declared payload to an unpublished `.new` path and require the
   exact declared byte count;
2. atomically rename it to a content-addressed immutable final filename;
3. commit its generation/profile/name/SHA-256/dimension identity in SQLite; and
4. publish the regenerated manifest through `manifest.json.new` plus atomic
   rename.

The manifest projects active sidecars for its semantic generation. A database
commit with the old manifest is reported as `stale-sidecars`; authorized
recovery regenerates it. `verifyragstore` now checks sidecar lifecycle rows,
generation/profile identity, safe filenames, presence, and actual file bytes
against the committed SHA-256. Missing or changed sidecars fail verification.
Historical and superseded sidecars remain immutable, rebuildable artifacts and
are not projected as active.

`ragbackup.crexx` exposes a staged backup session plus one-shot backup/restore.
It pins a read transaction and published generation, uses the generic SQLite
online-backup API, copies only active matching immutable sidecars, generates a
manifest from the backed-up database, verifies the assembled staging folder,
closes the read snapshot, and atomically renames the folder into place. A live
writer opened before the backup advances the source to generation 3 while the
backup remains entirely at generation 2. Restore first verifies its source and
always targets a fresh folder through the same staged publication discipline.

## Narrow Level-B Foundation Exception

The installed Level-G surface has `rxhash.sha256` but no binary file-read API.
`ragfile.crexx` is therefore a minimized Level-B foundation module using only
the VM's byte-preserving `freadb`/`fwriteb` instructions. It delegates hashing
to installed `rxhash` and owns no library, sidecar, backup, or restore policy.
The language-level audit names this exact exception and requires its inline
rationale; every maintained application and test consumer remains Level G.

The binary proof writes and reads ten bytes containing two NULs and invalid
UTF-8, compares `sha256file` with in-memory `rxhash.sha256`, and rejects a size
ceiling below the file length in all four compiler/runtime cells. Sidecar
verification has a 2,147,483,647-byte ceiling and uses one-shot memory because
incremental/file hashing is not in the consumed CREXX capability. That known
scaling limit remains in the parallel capability backlog and is not hidden in
native product code.

## Focused Proof

CTest `p2_05_backup_restore` compiles `ragschema`, `ragfile`, `ragstore`,
`ragbackup`, and its Level-G scenario with and without optimization and runs
both VMs. Every cell proves:

- binary-safe file transfer and exact installed SHA-256;
- immutable-path, unsafe-id, noncanonical-checksum, and overwrite denial;
- active sidecar manifest/SQLite agreement and byte checksum verification;
- a generation-2 online snapshot while a live writer publishes generation 3;
- exactly the generation-2 sidecar and semantic rows in the snapshot;
- complete snapshot and restore verification;
- source snapshot zero-write during restore;
- fresh-target enforcement; and
- checksum-tampered and missing active-sidecar detection.

CMake independently hashes the source, snapshot, and restored sidecars. All
three SHA-256 values are identical to the committed identity.

The optimized crash matrix sends real `SIGKILL` to both VMs at four sidecar
boundaries: prepared temporary file, installed orphan, committed SQLite row,
and temporary manifest. Uncommitted files never become active; committed rows
report stale manifest state and recover to aligned, verified state.

Both optimized VMs are also killed after the database, sidecars, and manifest
stages of backup and restore. Each of those twelve process terminations leaves
the final target absent and only the expected `.new` staging contents. The
source bundle remains filename/size/mtime/SHA-256 identical across each crash
sequence.

The isolated focused CTest passed in 40.89 seconds with 227,776 KiB maximum
RSS. The focused test also passed in the full parallel Debug run in 50.19
seconds.

## Remaining Limits

- Sidecar content is rebuildable; source revisions and claim support are not.
- Online writer concurrency assumes the live writer has already selected WAL;
  attempting to start a new writer after a rollback-journal reader pins the
  database fails safely rather than changing the pinned snapshot.
- The current hash path is bounded and one-shot as described above.
- P2-06 owns paged repositories and complete lifecycle/orphan invariants.
- P2-07/P2-08 own public command/result and lifecycle command surfaces.
- Exact downstream Linux confirmation remains later QA after further material
  current-host progress.

`P2-06` is next and pending. No later Phase-2 item is active or implied complete
by this result.
