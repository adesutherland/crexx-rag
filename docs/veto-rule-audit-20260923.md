# Veto-rule audit — 23 September 2026

The reported batch-size refusal is overbroad. Remove the whole-configuration equality veto, while retaining the immutable inputs and provider-request checks for the work actually being resumed. Reverting an unrelated completed-phase setting is a workaround for that rule, not a justified requirement of graph processing.

This dated source audit was captured before the accompanying implementation. Its recommendations are not an instruction to change a live corpus. Baseline: clean `main`, `4413fce7f36bd4909a816b713e873c7ed3fd874b`. At audit capture, no product code, corpus, configuration, job, installed executable or release had been changed. The [roadmap](ROADMAP.md) records the subsequently implemented repair and current status; recommendations below are not automatically accepted backlog commitments.

## Scope and meaning of “all”

The catalogue covers the veto families found across 88 production Level-G source files (application, CLI/MCP/ADDRESS surfaces and provider adapters), repository instructions and repository agent skills. Repeated checks in different adapters are grouped by their rule and owner. Ordinary malformed arguments, missing files, SQL/I/O failures and individual numeric bounds are grouped rather than presented as thousands of separate policies. Silent eligibility filters and review dispositions are included, not just error strings.

This is a repository-wide static inventory, not a claim that every runtime path has been executed. The installed version and the specific four-worker incident were not inspected. Only the reported guard received the isolated predicate check described below. Existing tests were inspected for context; no new full-suite or live-provider qualification is claimed. Build/release gates are covered as development instructions, not counted as corpus execution rules. External host approval systems and restrictions outside this repository are outside this audit.

**KEEP** means retain the underlying stop or hold. **NARROW** means retain a justified protection but remove its unrelated scope or unnecessary failure. **REMOVE** means remove that veto, sometimes returning an idempotent success instead. These are recommendations, not current behavior.

Primary recommendations for the 86 families: **62 KEEP, 18 NARROW, 4 REMOVE, and 2 KEEP REMOVED**. Some KEEP rows also call for clearer diagnostics or easier recovery; the counts use the first recommendation in each row.

## The reported failure

`worksnapshotmatches` compares the saved and current profile hashes, then requires either the full configuration hash or full effective JSON to match. Its only excluded field is `$.config.workers.processes`. It never asks whether the changed field is relevant to the remaining job items. [ragconfiguration.crexx:53](../crexx/application/ragconfiguration.crexx#L53)

The check is used by public launch preflight, worker launch, continuation, and again before individual provider work. Changing just the first preflight would therefore leave the same veto deeper in execution. [ragproduct.crexx:1043](../crexx/application/ragproduct.crexx#L1043) [ragprocess.crexx:547](../crexx/application/ragprocess.crexx#L547) [ragcontinuation.crexx:24](../crexx/application/ragcontinuation.crexx#L24) [ragapplicationprovider.crexx:127](../crexx/application/ragapplicationprovider.crexx#L127)

The exact SQL predicate, extracted from source, was evaluated against a synthetic in-memory SQLite snapshot:

| Change | Predicate permits it |
| --- | --- |
| None | Yes |
| Workers 1 → 4 | Yes |
| Embedding batch 100 → 1,000 | No |
| Both changes | No |

This confirms the mechanism, not the state of the reported live job. The operational canonical form already includes role batch size, while the semantic role projection excludes it. [ragcanonical.crexx:99](../crexx/application/ragcanonical.crexx#L99) [ragcanonical.crexx:182](../crexx/application/ragcanonical.crexx#L182)

Existing recovery coverage explicitly rejects a changed model and permits a changed worker count. It does not establish acceptance of the reported unrelated batch change. Those two controls should be retained when adding the new regression. [WorkerRecovery.cmake:190](../cmake/WorkerRecovery.cmake#L190)

Recommended repair: use the pending item's source/role/provider and actual frozen prompt/schema/input to determine compatibility. Permit unrelated settings and appropriate operational tuning. Preserve old snapshots, receipts and cumulative usage; changing a configuration file must not silently renew a job budget. The existing selected-source/role replay comparison is a useful starting point, but **do not simply replace the full hash with the semantic hash**: maintenance prompt/schema and request-envelope checks also matter. Runtime provider creation still consumes current configuration. [ragconfiguration.crexx:16](../crexx/application/ragconfiguration.crexx#L16) [ragapplicationprovider.crexx:133](../crexx/application/ragapplicationprovider.crexx#L133) [ragapplicationprovider.crexx:233](../crexx/application/ragapplicationprovider.crexx#L233)

## Recommended order

1. **V01/V02:** remove whole-configuration worker vetoes in their shared owner and verify all four consumers. Start with the supplied batch-size case and a changed relevant request as a refusal control.
2. **V03/V04/V06:** restore independent reads and rejection/closure paths; preserve relevant evidence/effect checks.
3. **V09/V22:** stop requiring unused providers or funding for the entire requested worker pool before any useful work can run.
4. **V05/V14/V16/V17:** reduce unrelated plan/query/report invalidation. Preserve exact action, affected evidence, deadlines and atomic publication.
5. **V11/V53/V67–V70:** separately evaluate compiled native pins, model-confidence gating and scale/format envelopes against concrete workloads.
6. **V75/V76/V78/V80:** align agent guidance so existing authority and supported recovery are actually used.

For the first repair, regression coverage must include: changed embedding batch with retained graph work; changed operational timeout/polling without changing request meaning; unrelated source/provider addition; real provider/model/prompt/schema/input mismatch; unchanged receipts/usage; no implicit allowance renewal; normal worker-count changes; and public launch, continuation and per-item execution agreeing. Passing the isolated SQL probe is not enough to qualify that repair.

My recommendation is to keep vetoes that prevent a concrete wrong write, duplicate paid call, unauthorized spend, invalid evidence or unsupported operation. Remove dependence on unrelated state, make repeat no-ops succeed, and make temporary capacity shortages wait. Every remaining refusal should identify the affected item, exact binding and one supported next action.
